# 0004 id・README・まとめた書き出しの作り方

- 日付：2026-11-15
- 状態：決定（ユーザーが 0003 の ②③ の実装を了承。Fable の設計レビュー 12 件を反映）
- きっかけ：0003 の作る順番 ②（`id` と `README.md`）と ③（まとめた書き出しと取り込み）を作る。何を持つかは 0003 で決まっているので、ここでは「どう作るか」を決める

## 決めたこと

1. **`id` は ULID。** core に生成関数を置く（純粋な TypeScript、依存なし、乱数は `crypto.getRandomValues`）
2. **新しいページは作るときに `id` と `created_at` を書く。** `created_at` は `YYYY-MM-DDTHH:mm:ss+09:00`（端末の時間帯の設定によらず日本時間）。既存ページには `created_at` を後から付けない（ULID の先頭 10 文字が作った時刻なので足りる）
3. **既存ページへの `id` 付けは「移行」として、管理者が画面のボタン（「データを今の形にそろえる」）で流す。** 自動では流さない
   - 押すと、まずページだけの控え（下の 5）を保存し、それから付ける。画面に「何件に付けるか」を出す
   - 書き込みは今のファイル API（`PUT /file`、revision 条件付き）。新しい口は作らない
   - 保存先と一致している内容に項目を 1 つ足して書く。部屋の書き出し待ちの分には触れない。開いている部屋は次の書き出しのときに 3-way マージ（props はキーごと）で取り込む
   - ドライブの条件付き書き込みは「確かめる → 書く」の 2 往復で、原子的ではない。部屋が書き出した直後の内容を古い内容で上書きしないよう、**2 分以内に更新されたページは飛ばし**、条件が合わなかったページも飛ばす。画面に「数分おいてもう一度」と出す。何度流しても同じ結果になるので、押し直せば続きから付く
   - 通信などで失敗した 1 件では止めず、件数を出す
   - `id` が重複していたら、パスの順で最初の 1 件を残し、残りに振り直す
   - frontmatter が読めないページは飛ばし、件数を知らせる
4. **`README.md` は core の関数で文章を作る**（型の台帳ができたら型の一覧もそこから）。サーバーだけが書く
   - 書くのは「プロジェクトを作るとき」と「管理者のそろえるボタン」（`POST /api/projects/:id/readme`、管理者だけ、受け取るものは無い）の 2 か所だけ。同じ中身なら書かない
   - 開くたびには書かない（全員が書き合う、README が無いときに 2 人が同時に開くと 2 枚できる、版の違う環境が書き直し合う、ページ一覧の 1 リクエストのドライブ呼び出しが上限 50 に近づく）
   - 文面が変わるのは書き方の決まりを変えるときで、それはもともと移行。そろえるボタンで当てる
5. **まとめた書き出しは zip で、中身はドライブのフォルダと同じ形**（`README.md`・`pages/`・`assets/`）。新しい形式を作らない
   - ブラウザで作る（Worker の CPU 10ms を使わない）。zip は `fflate`（client に依存を 1 つ足す）。画像は読んだ順に流し込み、全体を 2 重に持たない
   - 「ページだけ」も選べる。移行の前に自動で取る控えはページだけ（移行が触るのはページだけで、画像込みはスマホで重い）
   - `README.md` はドライブから読まず、同じ core の関数で作る
   - 同じ名前のファイルが複数あれば（ドライブは許す）、2 件目以降を「題名 (2).md」として入れ、件数を知らせる
   - メンバー全員が使える
6. **取り込みは、その zip を今のプロジェクトへ「無いものだけ」書く。** 上書きはしない
   - ページは、今あるページと**題名（同一視で）か `id` が同じなら飛ばす**。zip の中の重複も先に除く。古い名前の写しで `id` が重複し、生きているページの `id` が振り直されるのを防ぐ
   - ページのファイル名は題名の決まりにそろえる。画像の名前はページから参照されるので変えない
   - ページは 1 件ずつ、画像は 3 件ずつ書く
   - `pages/`・`assets/` の直下以外は無視する（展開してフォルダごと zip にし直したものは、先頭のフォルダ 1 つを外して読む）
   - 管理者だけが画面に出る
7. 一覧の表示では、`id` と `created_at` を出さない。隠す項目は core の `HIDDEN_PROPS` の 1 か所に置く
8. **`id` は「無いことがある」。** frontmatter が読めないページ、そろえる前のページ、取り込んだ直後のページ、外で `id` を消されたページには無い。`id` を使う側（索引・API）は、無い場合を扱う

## 関所ができるまでの暫定

- **ファイル API の例外の使い道が 2 つ増える**（`id` の移行と取り込み）。一括と移行は本来関所（Command）を通すが、0003 の順番で ②③ が ⑤ より先なので、今の口を使う。Command ができたら関所へ移す
- 「管理者だけ」は、移行と取り込みについては画面での制限。サーバーの `PUT /file` はメンバーなら通る（今もページの作成・保存がそうであるのと同じ）。README の書き込みは、サーバーで管理者に限っている

## 他の案

- 保存するたびに、`id` が無ければ付ける（遅延付与）：移行が要らないが、部屋とファイル API が同時に別の `id` を付けて競合しうる。開かれないページにはいつまでも付かない
- サーバーに移行用の口を作る：一括の正式な経路は関所でやるべきで、関所の前に専用の口を増やすと例外が増える
- 書き出しを JSONL にする：AI には読みやすいが新しい形式になる。zip ならドライブと同じ形で、展開すればそのまま読める
- 書き出しをサーバーで作る：CPU 10ms と 1 リクエストの外部呼び出し 50 回に収まらない
- README をページ一覧の読み込み時に比べて書き直す：上の 4 の理由でやめた

## 難しくなること

- 移行がブラウザ任せになる：途中で閉じると一部だけ付く（押し直せば続きから付く）
- 移行のあと、開いている各端末は 10 秒おきの取り込みで、変わったページを 1 件ずつ読み直す（500 ページなら端末ごとに 500 リクエスト。1 日 10 万の枠には収まるが、数分かかる）
- 取り込みは件数分のリクエストになる（数百件なら数分）
- 画像込みの書き出しは、画像の合計の大きさだけブラウザのメモリを使う（画像の縮小は 0003 のリスクにある別の PR）
