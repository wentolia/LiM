# 0001 設計思想とデータの決まり

- 日付：2026-11-15
- 状態：決定
- 元の文書：「SABAKAN 設計思想と決まり事」（https://claude.ai/artifact/AS2DvXJQoFNr7TGbAZi8LQ 。比較した案と現状のコードの問題点はそちらにある）

## 決めたこと

**データはドライブの 1 か所に、構造は台帳の 1 か所に、書き込みは関所の 1 か所に置く。** この 3 つを守り、機能の追加・変更・削除、移行、外付け AI による読み込みと操作を、その場しのぎの仕組みなしに扱う。

そのため、コアの要素を Page・Query・View の 3 つから、Type（形）と Command（書く）を足した 5 つにする。

### 原則（11 個）

| # | 原則 |
| --- | --- |
| 1 | コアは 5 要素：Page（1 件）・Type（形）・Command（書く）・Query（選ぶ・集計する）・View（描く） |
| 2 | データが主、アプリは従。利用者のデータの正本は、人が読めるファイル（Markdown＋frontmatter） |
| 3 | データは自分を説明する。ドライブのフォルダに、形式の版と型の定義の写しを置く（置き場とファイル名は、新しいファイル形式なので実装前に別の記録で決める） |
| 4 | 宣言は 1 か所、その他は生成。型と Command は台帳に書き、検証・データ地図・API の説明・AI 用の道具の定義をそこから作る |
| 5 | 書き込みの関所は 1 つ。props の変更・作成・削除・一括は、画面・AI・同期・取り込みのどれも同じ Command を通る。本文の打鍵は部屋（Yjs）で受け、部屋がドライブへ書き出すときに同じ検証を呼ぶ |
| 6 | 派生物は捨てられる。D1 は「運営データ（正本）」と「索引（派生物）」の 2 種類だけ |
| 7 | 外から指すときは変わらない ID。中のリンクは `[[題名]]` のまま |
| 8 | 機能は着脱できる単位。データは機能より長生きする |
| 9 | 自分の画面も外部と同じ口を使う。読むのは同じ Query、props の変更・作成・削除・一括は同じ Command。本文の共同編集だけは部屋 |
| 10 | 足す前に測り、足したら書く。新しい表・形式・経路・常時動く処理は、今あるもので表せない理由と無料枠の見積もりを書いてから |
| 11 | 最後に決めるのは人。AI 用トークンには当面、一括・改名・削除を許さない |

### 判断が分かれた点

| # | 論点 | 決定 |
| --- | --- | --- |
| A | 利用者データの正本 | ドライブの Markdown。D1 の索引（1 ページ 1 行、評価は core の Query）を必須にする |
| B | 型をどこで定義するか | 組み込みはコードの台帳（`packages/core/src/schema/`）。利用者定義の型は後で検討。今は台帳だけ作る |
| C | 識別子とリンク | frontmatter に不変の `id`（ULID）。props も本文も `[[題名]]` のまま書き、索引が `id` を引く |
| D | 書き込みの経路 | 関所（Command）は 1 つ。1 件の変更は部屋へ、新規作成・一括・移行は関所からドライブへ（revision 条件付き）。開いている部屋は次の書き出しで 3-way マージして取り込む。関所は Command の入口と部屋の書き出し時の 2 か所で同じ core の関数を呼ぶ |
| E | 件数の多い記録の置き方 | 1 件 1 ファイルで始める。一括は 1 回の件数に上限を設け、続きはカーソル（条件付き書き込みは 1 件 2 往復なので目安 20 件。実装時に測って決める） |
| F | フォルダ構成 | すべて `pages/`（型は frontmatter だけ）。分けたくなったら移行で `records/<id>.md` へ |
| G | 集計の置き場 | Query の一部（JSON の構造を正とする）。View は描くだけ。Query のキーは 4 つから増える |
| H | 外部の口 | REST（`/api/v1`）が本体、MCP は台帳から生成する薄い層 |
| I | 「このブラウザだけ」モード | **廃止**（推奨は「凍結」だったが、ユーザーが廃止を選んだ） |
| J | 機能の入れ方 | リポジトリ内のモジュール。実行時プラグインは作らない |
| K | 変更履歴 | D1 に操作の記録（直近分）＋ Page の `updated_by`。取り消しはドライブの版履歴とゴミ箱 |
| L | AI による一括・削除の承認 | 当面 AI 用トークンに一括・改名・削除を許さない。必要になったら「提案」Page と承認画面を足す |
| M | Google カレンダー／ToDo 同期の置き場 | Worker に内蔵（Cron と変更通知）。`actor: sync` として Command を通す。実装前に記録とスコープ追加の了承を経る |

### データの細かい決まり

- 予約された項目名：`id`、`type`、`tags`、`created_at`、`updated_at`、`updated_by`、`ext`（外部 ID。例：`ext.gcal`）。機能ごとに内部用の項目を増やさないため
- 金額は整数（円）、日付は ISO 形式。比較や集計を推測ではなく宣言された種類で行うため
- 書き手の記録は `actor {kind: user|token|sync, id, via}`。誰が何をしたかを、人・トークン・同期で同じ形で追うため
- AI 用トークンにできないこと：一括・改名・削除に加え、メンバー管理・トークン発行・ドライブの接続。全員のデータへの鍵と権限に触れるため

## なぜ

- 機能と役割が増えても「今のデータ構造」を 1 か所（台帳とデータ地図）で見続けるため
- 書き込みの経路が機能ごとに増えると、検証・権限・記録の抜け穴が生まれるため
- 移行と外付け AI の読み込みには、人が読めるファイルと不変 ID が最も強いため

## 前の決まりから変えたこと

- 「コアは 3 要素」「型の定義も Page」「集計は View の一種」「Query のキーは 4 つで固定」「ページ内容の変更はすべて部屋を通す」（CLAUDE.md の旧版）
- 前の設計書（AI 連携・Google 同期）の「型 Page」「集計 View」
- 「このブラウザだけ」モードを廃止する
- パスの決まりとリンクの書き方は変えない（`id` を足すだけ）

## 他の案と、難しくなること

- 型を Page で定義する案：家族が画面から型を作れるが、誤編集で財務が壊れる。台帳はコード変更が要るぶん、型の追加は開発者の作業になる
- すべての書き込みを部屋経由にする案：経路は 1 つになるが、一括で件数分の部屋を起こし無料枠を圧迫する。関所案は「関所」と「部屋の書き出し」の 2 か所で同じ関数を呼ぶ規律が要る
- 「このブラウザだけ」モードの廃止：ログインなしで試す手段がなくなる。代わりに書き込み経路とテストが 1 つで済む

## 必要になるまで作らないもの

機能ごとのオン／オフと「試験中」の印、API トークンの型ごとの範囲、`idempotency_key`、型ごとの CSV 書き出し、アプリ内のデータ地図画面、索引から SQL への Query の翻訳、Webhook。
